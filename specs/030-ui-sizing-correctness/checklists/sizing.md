# Sizing Requirements Quality Checklist: Application Interface Sizing Correctness

**Purpose**: Interrogate the sizing and interaction requirements themselves, as
written, for completeness, clarity, consistency, and measurability. This feature
exists because three prior attempts shipped with green tests, so the question
this checklist answers is whether every sizing invariant is stated as an
observable, frame-level condition that a check could fail on, and whether the
drag, resize, and toggle interaction matrix is fully enumerated.

**Created**: 2026-07-25

**Feature**: [spec.md](../spec.md)

**Note**: This checklist is generated by the `/speckit-checklist` command based on
feature context and requirements. It validates the requirements, not the
implementation.

## Invariant Observability

- [ ] CHK001 Is every sizing invariant stated as a condition observable on a
      single rendered frame, rather than as an outcome observed after an
      interaction settles? [Measurability, Spec FR-010]
- [ ] CHK002 Is the quantity that must never be exceeded during a splitter drag
      named precisely enough to be read off one frame (which edge, of which
      element, compared against which other edge)? [Clarity, Spec FR-010]
- [ ] CHK003 Is "the intrinsic extent" defined by what it excludes as well as
      what it includes, so a reader can decide for any given element whether it
      contributes? [Clarity, Spec FR-001, FR-007]
- [ ] CHK004 Is the tolerance for every "equals" comparison stated (hairline,
      one point, exact), so a check cannot pass or fail on rounding? [Clarity,
      Spec FR-014, SC-003]
- [ ] CHK005 Can "no gesture may be stopped by a minimum that a later gesture
      would relax" be evaluated without knowing the platform's resize mechanics?
      [Measurability, Spec FR-003]
- [ ] CHK006 Are the requirements distinguishable from the arithmetic they
      constrain, so that a check satisfying the arithmetic alone would not
      satisfy the requirement? [Clarity, Spec FR-018]

## Interaction Matrix Coverage

- [ ] CHK007 Are requirements defined for each gesture in isolation (window
      resize, splitter drag, log toggle) and for each pairwise combination?
      [Coverage, Spec FR-010]
- [ ] CHK008 Are requirements defined for the frame during a gesture, not only
      for the frame after it commits? [Coverage, Spec FR-010, FR-011]
- [ ] CHK009 Are requirements defined for both axes independently and for a
      corner drag that moves both at once? [Coverage, Spec FR-003]
- [ ] CHK010 Are requirements defined for the first frame after restore, before
      any user gesture has occurred? [Coverage, Spec FR-012]
- [ ] CHK011 Are requirements defined for a gesture that begins immediately after
      a different gesture ends, with no settled frame between them? [Gap]
- [ ] CHK012 Is the behavior specified when the pointer moves faster than frames
      are produced, so a gesture spans a large jump in one frame? [Edge Case,
      Spec Edge Cases]
- [ ] CHK013 Are requirements stated for the log-open and log-closed variants of
      every window-sizing requirement, rather than only the closed case?
      [Coverage, Spec FR-006]

## Boundary And Growth Rule Clarity

- [ ] CHK014 Is the log pane's upper boundary derived from a single named
      quantity, with no second definition elsewhere in the spec that could
      diverge? [Consistency, Spec FR-010, FR-013]
- [ ] CHK015 Is the growth rule for the modal specified precisely enough that two
      readers would compute the same size for the same window? [Clarity, Spec
      FR-015]
- [ ] CHK016 Are the modal's floor, ceiling, and maximum-fraction bounds stated
      with their interaction order, so the result is unambiguous where two bounds
      both apply? [Clarity, Spec FR-014, FR-016]
- [ ] CHK017 Is "progressively smaller share of each addition" expressed as a
      property that can be checked at two window sizes, rather than as a
      narrative description? [Measurability, Spec FR-015]
- [ ] CHK018 Is the denominator for "half of the settings body" defined at a
      specific width and frame, so the fraction is reproducible? [Clarity, Spec
      FR-017, SC-004]
- [ ] CHK019 Is the condition under which the modal maximum may be raised stated
      as a measurement rather than a judgment call? [Measurability, Spec FR-017]

## Requirement Completeness

- [ ] CHK020 Are requirements present for every one of the three reported
      defects, with none reduced to an assumption or an edge case? [Completeness,
      Spec FR-001 to FR-017]
- [ ] CHK021 Are the behaviors inherited from the previous slice that this
      feature must not break (height-neutral toggle, proportional growth sharing,
      geometry persistence, six-line log floor) stated somewhere they can be
      checked, rather than only in Assumptions? [Gap, Spec Assumptions]
- [ ] CHK022 Is the trigger set for recomputing the enforced minimum enumerated
      exhaustively, so that "and only when" is decidable? [Completeness, Spec
      FR-005]
- [ ] CHK023 Are requirements defined for what the window does when the intrinsic
      content changes in each direction (grows, shrinks)? [Completeness, Spec
      FR-009]
- [ ] CHK024 Is the documentation obligation specified with enough precision to
      know which statements in the architecture of record are wrong today?
      [Clarity, Spec FR-022]

## Consistency With Prior Requirements

- [ ] CHK025 Do the log pane requirements here contradict or supersede any
      requirement from the original overlap report, and is the relationship
      stated? [Consistency, Spec FR-010]
- [ ] CHK026 Is the boot minimum's role (startup fallback, not the enforced
      minimum) stated consistently everywhere it appears, including in the
      architecture of record? [Consistency, Spec FR-002, FR-022]
- [ ] CHK027 Are the terms used for the same concept normalized across the spec
      (enforced minimum, intrinsic extent, content minimum, boot minimum), with
      no two names for one quantity? [Consistency]
- [ ] CHK028 Does any requirement in this feature permit changing a constant
      established by a previous slice, and is that permission bounded and
      recorded? [Conflict, Spec FR-017]

## Verification Obligation Quality

- [ ] CHK029 Is the anti-regression obligation stated as a property of the
      checks (what must make them fail) rather than as a mechanism (what tool to
      use)? [Clarity, Spec FR-018 to FR-021]
- [ ] CHK030 Is "reintroducing any one of the three defects turns the checks red"
      specific about what counts as reintroducing each defect? [Measurability,
      Spec FR-021]
- [ ] CHK031 Are the environmental constraints on the checks (no display, no
      game, no manual step) stated as requirements rather than assumptions?
      [Completeness, Spec FR-020]
- [ ] CHK032 Is the manual desk validation distinguished from the automated
      obligation, so neither is presented as a substitute for the other? [Clarity,
      Spec SC-005, SC-006]

## Edge Case And Assumption Validation

- [ ] CHK033 Is the display-work-area cap stated with its consequence (content
      may be clipped) rather than only its mechanism? [Clarity, Spec FR-008]
- [ ] CHK034 Is the decision to exclude a scrollable central area recorded with
      its reason, so it is not silently reversed later? [Assumption, Spec
      Clarifications]
- [ ] CHK035 Are the assumptions that carry forward untested behavior from the
      previous slice identified as risks rather than as facts? [Assumption, Spec
      Assumptions]
- [ ] CHK036 Are the edge cases involving persisted state from an older version
      (oversized window, out-of-range pane height) covered by requirements and
      not only by the edge case list? [Coverage, Spec FR-012]

## Notes

- Check items off as completed: `[x]`
- This checklist is evaluated during `/speckit-analyze`, before implementation
  begins. Items that fail are spec defects to fix, not implementation work.
- CHK001, CHK005, CHK008, and CHK030 are the highest-value items: each targets
  the specific way the previous three attempts passed their own checks while the
