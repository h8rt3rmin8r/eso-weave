# Input Safety

Synthesized Input means generated input, injected input, Windows `SendInput`, or
Linux `uinput` output. Those common names all refer to input emitted by ESO Weave.

ESO Weave intercepts exact current ESO combat chords only while the ESO client is
active and its window is focused. The chord evidence comes from PixelBeacon and
contains one keyboard or mouse primary plus normalized modifiers. Every other
input passes through. Generated input is flagged so the interception engine
never consumes its own output.

## Exact interception decision

The hook evaluates one physical event in this implementation order:

1. If the event was generated by ESO Weave, pass it through.
2. On primary Up, retire held-primary state. If the matching Down passed through,
   pass this release through too.
3. If ESO is inactive, pass through.
4. If the ESO window is unfocused, pass through.
5. If no exact, unique, valid native combat chord matches, or the action is
   inactive, pass through.
6. If ESO Weave is suspended and the action is not an application toggle, pass
   through.
7. If menu evidence gates input and the action is not an application toggle,
   pass through.
8. If life, roll-dodge, world, or travel evidence does not authorize weaving and
   the action is not an application toggle, pass through.
9. If the current physical modifiers cannot safely execute every required target
   chord, pass through. ESO Weave never releases a modifier held by the user.
10. Otherwise, a new primary Down copies one immutable skill, Attack, and optional
    Block plan into a non-blocking queue handoff. Repeated Down events do not
    enqueue again. The handled physical Down and Up events are suppressed.

Repeated Key Down events do not enqueue again. This preserved rule includes
native keyboard primaries; pointer buttons use the same one-handoff lifecycle.

Focus scoping is unconditional. No other condition replaces it, so suppression
outside the focused ESO window is unreachable by construction.

If the bounded handoff queue is full or disconnected, the callback logs a
warning and drops the action without blocking. The physical event has already
been classified as suppressed, so a dropped handoff does not replay the
original key later.

The menu gate can only relax interception. It is an additional early pass, so
for every combination of inputs the gated result is either identical to the
ungated result or more permissive. It starts closed. An addon too old to publish
the gate, a sample that fails validation, or a lost beacon signal keeps or
returns it to that fail-closed state. Unavailable menu evidence fails closed:
bound physical input passes through and autonomous features remain gated until a
positively decoded Gameplay surface returns.

## Worker boundary and cancellation

Interception callbacks only classify, suppress, and hand off. They never sleep,
block, or synthesize. Every timed sequence runs on a dedicated worker.

Before a queued weave begins, the worker verifies that the request's
authorization epoch is still current, its slot is active, Life State is Alive,
Roll Dodge is Inactive, World State is Active, Travel is Inactive, and the
current timing profile's Global Cooldown has elapsed. Losing focus, entering
suspension, or closing the menu gate invalidates the epoch. A request rejected
at this boundary is dropped and is never replayed, even if the gate reopens.

Native binding replacement or loss also advances the authorization epoch. The
old chord stops being intercepted immediately, and work admitted under the old
snapshot cannot start or continue.

The real input sink rechecks the authorization epoch and the shared life,
roll-dodge, world, and travel gates before every generated press and during
waits. If one closes during a sequence, remaining synthesis stops. Releases for
any application-owned primary or modifier already held by the sink still run in
reverse order. A modifier that becomes physically held is not released by the
application. A cancelled sequence
that emitted nothing does not consume the Global Cooldown.

Death closes the shared Life gate immediately and advances a monotonic death
epoch once for that open-to-closed transition. Dead, Unknown, and every
Recovering path remain closed. When the add-on finishes a death episode, the
reader republishes current safety and action observations before routing Alive,
so no pre-death cache value can become authorization merely because the gate
reopened.

Roll-dodge evidence fails open for physical input and closed for generated input.
Active or unavailable roll state passes the player's original skill key through.
The worker rechecks the gate before accounting cooldown, and the real input sink
checks it before every generated press and wait. If a roll begins during a
sequence, remaining synthesis stops and the sink still releases any mouse button
or other application-owned primary it already holds. Dropped work is never
replayed after the roll ends.

The application toggles for suspend, fishing, and Auto Potion remain reachable
while suspended. F1 changes suspension, and Auto Potion checks suspension before
acting on F3. Fishing receives suspension directly. Entering suspension cancels
its deadline without clearing the request, and neither enabling Fishing while
suspended nor resuming sends Interact. Recovery requires a fresh manual cast or
turning Fishing off and on after the other gates permit it.

See [Action Authorization](action-authorization.md) for the cross-feature truth
table.

## Platform backends

Windows uses `WH_KEYBOARD_LL` and `WH_MOUSE_LL` hooks plus `SendInput`, including
injected-event flagging. Keyboard controls, five mouse buttons, wheel directions,
and portable modifiers share the platform-independent native control model. The
weave worker raises Windows timer resolution with
`timeBeginPeriod(1)` when that worker starts and balances it with
`timeEndPeriod(1)` when the worker stops. The higher resolution is held only for
the weave worker lifetime. A slow low-level hook callback can cause Windows to
remove the hook, which is why the interception callback cannot block.

Linux grabs one physical keyboard and one pointer and polls both through evdev.
One uinput virtual device advertises their combined keys and relative axes plus
the full portable native-control set. Unrelated grabbed key, button, and relative
events are forwarded. This path sits below the display server and behaves
identically under X11 and Wayland. The shared safety decision remains
platform-independent. Focus still depends on an X11 or XWayland active-window
observation, so pure Wayland cannot positively authorize interception.

## Keybindings

Skills 1 through 5, Ultimate, Synergy, Attack, and Block follow the current valid
bindings in ESO's Controls menu. ESO Weave has no combat fallback and does not
write ESO bindings. Suspend defaults to `F1`, fishing to `F2`, and Auto Potion to
`F3`. These three desktop-owned application toggles are suspend-exempt. The
interface uses a capture-style rebinding control and rejects conflicting toggle
assignments. In other words, it rejects conflicting assignments among the three
desktop-owned toggles. Every interception remains scoped to the focused ESO
window.

These three application bindings are separate from fishing's generated Interact
Key, which remains independently configurable until S102. A
changed Fishing configuration turns requested work off without input before the
new key can be used. Pixel Bus tolerance and cadence changes stay on the reader
worker and never move work onto the input callback.
