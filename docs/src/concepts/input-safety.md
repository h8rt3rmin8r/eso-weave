# Input Safety

ESO Weave intercepts configured physical keys only while the ESO client is active
and its window is focused. Every other key passes through. Generated input is
flagged so the interception engine never consumes its own output.

The decision order preserves physical input whenever generation is unsafe:

1. If ESO is inactive or unfocused, pass through.
2. If the event was generated by ESO Weave, pass through.
3. If the key is not bound, pass through.
4. If life, world, travel, or roll-dodge evidence cannot authorize synthesis,
   pass through.
5. If a menu or text field is open, pass through.
6. If ESO Weave is suspended and the action is not a toggle, pass through.
7. Otherwise suppress the physical key and enqueue the configured action.

Focus scoping is unconditional. No other condition replaces it, so suppression
outside the focused ESO window is unreachable by construction.

The menu gate can only relax interception. It is an additional early pass, so
for every combination of inputs the gated result is either identical to the
ungated result or more permissive. An addon too old to publish the gate, a sample
that fails validation, and a lost beacon signal all resolve to **no menu** for
interception, matching behavior when no menu gate exists. Autonomous features
still require their own positive safety evidence before generating input.

Roll-dodge evidence fails open for physical input and closed for generated input.
Active or unavailable roll state passes the player's original skill key through.
The worker rechecks the gate before accounting cooldown, and the real input sink
checks it before every generated press and wait. If a roll begins during a
sequence, remaining synthesis stops and the sink still releases any mouse button
it already holds. Dropped work is never replayed after the roll ends.

Interception callbacks only classify, suppress, and hand off. They never sleep,
block, or synthesize. Every timed sequence runs on a dedicated worker. The worker
and real input sink recheck safety before generated operations. If a gate changes
mid-sequence, remaining work is discarded and is never replayed later.

The application toggles for suspend, fishing, and Auto Potion remain reachable
while suspended, but reachability does not authorize them to act. All generated
input remains stopped while suspension is active.

## Platform backends

Windows uses a `WH_KEYBOARD_LL` hook and `SendInput`, including injected-event
flagging. The weave worker raises Windows timer resolution with
`timeBeginPeriod(1)` when that worker starts and balances it with
`timeEndPeriod(1)` when the worker stops. The higher resolution is held only for
the weave worker lifetime. A slow low-level hook callback can cause Windows to
remove the hook, which is why the interception callback cannot block.

Linux uses an evdev grab of the physical keyboard and a uinput virtual device.
This path sits below the display server and behaves identically under X11 and
Wayland. The shared safety decision remains platform-independent.

## Keybindings

Every binding is configurable. Skills 1 through 5 default to `1` through `5`,
Ultimate to `R`, Synergy to `X`, suspend to `F1`, fishing to `F2`, and Auto Potion
to `F3`. The three application toggles are suspend-exempt. The interface uses a
capture-style rebinding control and rejects conflicting assignments. Every
binding remains scoped to the focused ESO window.
